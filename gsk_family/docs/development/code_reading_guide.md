# Code Reading Guide

> **Orientation.** A guided tour for anyone opening `gsk_family` for the first
> time. It does not assume you know GSK, the CEC benchmarks, C++, or MATLAB - it
> tells you where to start reading and how the two language halves connect at the
> `gskcec_eval` MEX bridge.

For the plain-English "what is this and why" overview, read the
[explainer](../getting-started/explainer.md) first; this guide is the map of the
code. When you are ready to build or contribute, see the
[Developer Guide](developer_guide.md) and [Contributor Guide](contributor_guide.md).

## The 60-second mental model

The project answers one question reproducibly: *how well do the seven GSK
optimizers solve the standard CEC benchmark problems, compared to published
results?* It has two halves that meet at a thin bridge:

```text
  MATLAB                         C++  (benchmarks/)
  src/optimizers/*   --calls-->  gskcec_eval MEX bridge --calls--> CEC function ports
  (the algorithms)               (build/mex/)                      (the problems)
        |                                                                  |
        v                                                                  v
  src/runners/run_experiment.m  --writes-->  results/*.csv  --checked vs--  benchmarks/cec_reference_results
                                                                            (published tables + curated curves/logs)
```

- The **algorithms** (how to search) are MATLAB, under `src/`.
- The **problems** (what to solve) are C++, under `benchmarks/cec_suite_cpp/`.
- The **tools** that run, time, and check everything are C++ CLIs under
  `benchmarks/cec_suite_cpp/cec_tools/`.

## Where to start, by what you want to understand

**"What does one optimizer look like?"** Open
`src/optimizers/gsk/gsk_optimize.m`. Its help block cites the exact reference
file and links the input/output contract (`docs/reference/matlab_interface.md`). Baseline
GSK is the simplest; the other six are variations next to it.

**"What does a port of a non-MATLAB reference look like?"** Open
`src/optimizers/dt-gsk/`, ported from the Python DT-GSK reference
implementation (v2.46, MIT license). Start with `README.md` (dimension tiers,
seeding exception, validation record) and `docs/algorithms/dt-gsk.md`, then
`dt_gsk_config.m` (every setting of
the published `pub` profile, grouped by dimension tier), then
`dt_gsk_optimize.m` (the whole optimizer, eGSK-style: one file with local
helper functions) and `dt_gsk_graph.m` (the interaction graph used from
`D = 50`). Unlike the other six it does not use the shared `src/common` RNG and
fair-start helpers: it builds named Threefry substreams from `options.seed`
and samples its own `NP = 5*D` population; the runner's special handling is
`is_unified_only` in `src/runners/run_experiment.m`.

**"What does one benchmark problem look like?"** Open
`benchmarks/cec_suite_cpp/cec2017/src/cec2017_problem.cpp`. The header cites the
reference MEX file (with a SHA256) and lists every preserved quirk. Every port
implements the same tiny interface,
`benchmarks/cec_suite_cpp/cec_tools/include/gskcec/benchmark/benchmark.hpp`:
`evaluate(x)`, `bounds()`, `optimum()`, `dimension()`.

**"How do I run an experiment?"** Start at the CLI
`benchmarks/cec_suite_cpp/cec_tools/src/cli/gsk_run.cpp` (it validates the request, calls
MATLAB, then auto-verifies), which drives `src/runners/run_experiment.m` (the
loop that runs each optimizer and writes the result CSVs).

**"How are results checked?"** `benchmarks/cec_suite_cpp/cec_tools/src/experiment/comparison.cpp`
loads a run's per-dimension `summary/` tables and the matching published table
and produces the `CONSISTENT`/`DEVIATES` verdict (`summary/verification.json`).
See `docs/reference/result_schema.md`.

**"How do I know the ports are correct?"** The C++ tests under
`benchmarks/cec_suite_cpp/cec_tools/tests/unit/` compare each port against fixed-vector ground
truth generated from the original reference implementations (the data lives in
`tests/data/`, regenerated by the MATLAB scripts in `scripts/`). Rebuild the
C++ tree after C++ source/header, CMake, CLI/config, comparison, suite-port, or
test changes, then run them with `ctest --test-dir build --output-on-failure`.

## Reading order for the whole codebase

1. `docs/getting-started/explainer.md` - the concepts in plain language.
2. This guide, then `docs/reference/project_structure.md` - where things live.
3. `benchmarks/cec_suite_cpp/cec_tools/include/gskcec/` - the small set of C++ interfaces
   (`core/` types and bounds, `benchmark/` the problem interface + factory,
   `experiment/` config/comparison). Read the headers; they are short.
4. One benchmark port (`cec2017_problem.cpp`) and one optimizer
   (`gsk_optimize.m`).
5. The three CLIs (`gsk_list`, `gsk_validate`, `gsk_run`) - the user-facing
   surface.
6. `docs/reference/architecture.md` and `docs/reference/porting_notes.md` - the design and the
   per-suite fidelity record.

## Conventions you will see everywhere

- Ported files keep short historical source filenames or provenance notes in headers
  comment; behavior gaps are documented in `docs/reference/porting_notes.md`, never
  invented.
- Numbers come from the reference. Preserved quirks (things that look wrong but
  match the reference) are named and explained at the site, not silently fixed.
- C++ throws exceptions that name the suite/function/dimension/file on error;
  nothing depends on the current directory - data paths are always explicit.
- Reproducibility is deterministic: `gsk_run` and the shipped configs default
  to the reference seed policy, while root `run_all_cec*.m` launchers and
  direct `run_experiment(...)` calls default to unified fair-start mode.
  Unified seeds come from `get_cec_seed(base_seed, dim, func, run)` and exclude
  optimizer name, optimizer index, population size, suite name, and budget.
  DT-GSK is unified-only (that seed and `threefry` under every policy) and
  self-initializes instead of taking the runner's `X0`. Every actual seed is
  recorded; details are in `docs/reference/seed_policy.md`.
